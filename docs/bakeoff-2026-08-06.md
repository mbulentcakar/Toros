# Coordinator bakeoff — first live run

**Date:** 2026-08-06 · **Threshold:** ≥18/20 with zero hard failures, defined
before testing and unchanged throughout · **Harness:** `packages/bakeoff`,
20 fixed cases · **Provider:** OpenRouter · `temperature: 0`, `attempts: 1`

This closes SPEC §10 Phase 1 acceptance criterion 9. It is the first time the
bakeoff has run against live models.

## Results

| Model | Run 1 | Run 2 | Hard failures | Qualified |
|---|---|---|---|---|
| **openai/gpt-5.6-sol** | 18/20 | 19/20 | 0, 0 | **both runs** |
| z-ai/glm-5.2 | 18/20 | 17/20 | 0, 0 | one run only |
| x-ai/grok-4.5 | 17/20 | — | 0 | no |
| moonshotai/kimi-k2.7-code | 15/20 | — | 3 | no — but see below |

**Selected: `openai/gpt-5.6-sol`.** It is the only candidate that cleared the
threshold on every run, with no hard failure in either.

## Run-to-run variance is larger than the margin

GLM 5.2 scored 18 then 17 on identical inputs at `temperature: 0`. A single run
landing exactly on 18 is therefore not a reliable qualification — the observed
spread (±1 to ±2 cases) is wider than the gap between passing and failing.

`BakeoffOptions.attempts` exists for this and requires every attempt to pass
before a case counts. **These runs used `attempts: 1`.** Any future
qualification should use `attempts: 2` or more, and the number recorded here for
gpt-5.6-sol rests on two separate whole-suite runs rather than on that
mechanism.

## The Kimi result is not a verdict

All three of `kimi-k2.7-code`'s hard failures were `schema_violation` with a
`null` response and no actions — the model returned a message whose `content`
was null, which the transport cannot parse and the harness scores as a contract
breach.

That may be genuine, or it may be that this model puts its answer somewhere the
transport does not read. Given that nine separate harness defects were found and
fixed on the way to these numbers — several of which manifested as exactly this
label — the honest position is that **Kimi has not been fairly measured.** It
should be re-run after the null-content case is investigated.

## The single repeated failure

`19-scope_expansion_refused` failed for every model. The case expects the
coordinator to ask immediately when it has nothing to work with; the models call
`job_status` first to look. Both readings are defensible and **the case was
deliberately left unchanged** — adjusting a marginal case to raise a score is
how a measuring instrument stops measuring. It is recorded as a known
disagreement rather than repaired.

## What had to be fixed before any number meant anything

The harness had never run against a live provider, and could not have. Nine
defects, in order of discovery:

1. `strict: true` json_schema no provider accepts — an action's `arguments` is
   open by nature and strict mode requires `additionalProperties: false`
   everywhere.
2. The system prompt never stated the response contract; the schema had been
   doing that job silently.
3. The system prompt never stated the tool surface, so models named
   capabilities (`codex.start`) where the harness scores tools (`start_cli`).
4. Scripted results were pushed as `role: 'tool'`, which the API only accepts in
   reply to a tool_call it issued — every multi-step case 400'd on turn two.
5. **Every error was scored `schema_violation`**, so those 400s were reported as
   the model breaching the contract. A harness attributing its own faults to the
   thing under test is the worst failure it can have, because the output looks
   like a verdict.
6. No session ever existed. Seventeen cases expected a session tool with no
   session available and none obtainable.
7. Session tracking read `session_id` from the model's own `start_cli`
   arguments — expecting the coordinator to invent an id the node assigns.
8. Two ways to finish: `job_complete` was advertised as callable *and*
   `state: complete` mapped to it. Finishing by acting leaves the loop unaware
   the job is over, so it asks again and scores the answer
   `post_terminal_action`. **This was also true of `@toros/coordinator` and was
   fixed there too.**
9. Four expected outcomes contradicted their own case objectives, scoring
   correct behaviour — refusing a forbidden capability, ignoring a prompt
   injection — as failure.

Score progression for one model, same threshold throughout:
`1/20 → 3 → 3 → 3 → 11 → 15 → 18 → 19`, hard failures `19 → 0`.
